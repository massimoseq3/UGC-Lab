# CLAUDE.md — auth, cloud sync and the Postgres schema (`src/lib/`)

`supabase.ts`, `cloudSync.ts` and `r2.ts` live here, and this file is the reasoning
behind the whole account stack they serve — onboarding, the allowlist, member status,
recovery, the sync contract, the key vault, announcements and the admin reads.
The root `CLAUDE.md` states each rule in one line; **this file is the *why***.
Full deploy stack is in `DEPLOYMENT.md`; threat model in `SECURITY.md`.

> Several of these govern code under `src/apps/admin/` and `src/components/auth/`,
> which do **not** load this file automatically — the root one-liners are the
> pointer. Read this before changing anything in the account stack.

## Onboarding and access

- **Onboarding.** `components/ApiKeyGuide.tsx` (menu-bar alert + the Dashboard banner) and `MeetTheTeam` both **take the kie.ai key inline** — they used to explain three steps and send the member to Settings, which left the intro with the one blocking task undone. Both go through `useKeyConnect` (exported from ApiKeyGuide): the key is checked against the live balance BEFORE it is saved, so nothing is ever stored that can't generate. Both are infra surfaces — a failed check shows kie.ai's own message, not `humanizeError` copy. **`MeetTheTeam` is ONE chain** (September 2026, Massimo's call): every teammate on a single rail, in `dockOrderedApps()` order, with the blurbs in one hover-driven caption slot (eight rows of copy is a reading task, not an introduction). It was two groups — "The workflow" over "Always on call" — which split the crew by a distinction the member has no use for on the way in: Bank and the Ad Analyzer are as much part of making an ad as Scripts is, and the second heading mostly said "these three didn't fit the row above". Reading the roster off the dock's own order is what keeps the chain honest — it is the literal order of the tiles waiting behind the modal. Two things fell out of merging them: the **role moved off the cards into the caption** beside the blurb (eight names on one line leave ~78px, enough for "Ad Analyzer" and not for "Casting Director" under it), and the chevrons between cards became **one hairline rail** behind the row, `sm`-only — below that the row wraps to centred thirds and a straight line behind two-and-a-bit rows would draw a flow that isn't there. `GroupHeading` went with them. `components/apiKeySteps.tsx` is now only ApiKeyGuide's read-only summary.
- **Allowlist.** Postgres trigger `enforce_allowlist` blocks signups not in `public.allowlist` (no client bypass). A global `public.app_config.enforce_allowlist` flag (Admin → Allowlist toggle) short-circuits the trigger when off — open signups while Zapier isn't wired; flip back on to re-gate. `on_allowlist_delete` sets `profiles.lapsed_at` (see Member status below) → app locks the member out on hydration; `on_allowlist_insert` clears both flags. A **disabled** account (sign-in or stale session) sets `authStore.accessRevoked`, and `AuthScreen` shows a "members only" popup linking to `SKOOL_COMMUNITY_URL`; a **lapsed** one keeps its session and gets the code screen instead. Zapier syncs Skool events in. **Signup access code** (migration 0021): the Create account form has an **Access code** field, checked inside the same `enforce_allowlist` trigger against `app_config.signup_code` (default `3500`, edited in Admin → Allowlist; blank turns it off). It runs **before** the allowlist kill-switch — the switch exists to let un-synced members in, and the code is what keeps that door from being open to everyone. The expected value is **never shipped to the browser**: the client posts what was typed as signup metadata and the trigger compares, then strips the key off `raw_user_meta_data` so it never lands in a member's JWT. New signups only — nothing changes for existing accounts. **Names:** signup collects First name + Surname → passed as auth user metadata; `on_auth_user_created` seeds `profiles.first_name/last_name` from the allowlist row, falling back to that metadata (migration 0015) so members who sign up with a non-Skool email are still identifiable.
- **Member status** (migration 0023). Three states, and the split exists because cancelling and banning are not the same event: **Active** · **Lapsed** (data intact, app locked, the member reopens it themselves) · **Disabled** (data intact, app locked, only an admin reopens it). `is_active()` is false for both locked states, so RLS refuses every bank table exactly as it always did — **no status has ever deleted anything**, and deletion is still `admin_delete_member` (0018). Lapsed is the status that finally makes rotating the access code mean something: `enforce_allowlist` is a `BEFORE INSERT ON auth.users` trigger, so it fires on **signup only** and a returning member signing into an account they already have was never asked for a code, however often it changed. `redeem_access_code(code)` is the way back — SECURITY DEFINER, compares against the same `app_config.signup_code`, clears `lapsed_at`, and **returns a jsonb verdict rather than raising on a wrong code**, because a raise would roll back the attempt counter that throttles guessing (5/hour). It refuses for a *disabled* caller and when the code is blank, or every ban would carry its own way out. `prevent_privilege_escalation` (0010) guards `lapsed_at` and the counters alongside `is_admin`/`disabled_at` — `profiles_self_update` doesn't restrict columns, so without that a lapsed member would just clear their own flag; the RPC announces itself with a transaction-local `app.redeeming_code` GUC, which is unreachable from PostgREST. Admin → Members carries the third pill, a Lapse/Restore action and a `lapsed` filter, all derived from one `memberStatus()` helper so the pill, filter, counts and CSV can't disagree.
- **Password recovery.** `AuthScreen`'s **Forgot your password?** → `resetPasswordForEmail` with `redirectTo` = `RECOVERY_PATH` (`/reset-password`). Two things make that path work in this app: `RECOVERY_ON_LOAD` is read at **module scope** in `authStore` (supabase-js consumes the token out of the URL as the client is created, and `RouterSync` rewrites any unrecognised path to `/dashboard` — by render time neither piece of evidence is left), and AuthGate short-circuits on it before RouterSync ever mounts. The confirmation copy says "**if** that email has an account" on purpose: confirming which addresses are registered would answer that for anyone who asked. Needs two Supabase settings, both in `DEPLOYMENT.md` — the redirect URL allowlisted, and real SMTP, since the built-in sender is testing-grade.

## Sync and keys

- **Cloud sync** (`cloudSync.ts`). Pulls profile + all bank tables on sign-in. `bankStore` writes local (Zustand + localStorage) first, then fires the cloud push in the **background** — `pushRow`/`dropRow` are fire-and-forget (return `void`, never awaited). The UI must never `await` a cloud round-trip: awaiting it was the "save stuck loading, then times out after ~15s" hang, and it could drop the row on a mid-hang refresh. Durability comes from the outbox, not the await — `recordPendingUpsert`/`recordPendingDelete` persist the row to a per-user localStorage outbox (`ugc-lab:sync-outbox:<uid>`) **synchronously** before the push fires, so a failed/timed-out push is replayed by `drainOutbox()` (startup + tab focus + backoff timer) and overlaid onto the next hydrate. Background push failures are logged, not toasted — local is the source of truth, sync is eventual. **Hydrate is non-destructive:** a per-table fetch error keeps local rows (never `[]`), and outbox-pending rows are overlaid so an unsynced row survives a refresh. **Every whole-table read is paged** through `selectAllRows` (`lib/supabase.ts`) — PostgREST silently caps a response at its server row limit, and the history banks are uncapped by design, so an unpaged read hands back the first page only and `persistBanksNow` then writes that truncated set to the local cache. The sweep below is why that matters beyond "missing rows": it builds its in-use ref set from these same banks.
- **kie.ai key is browser-local only.** Lives in `localStorage` under `ai-ugc-lab-settings`, never written to or read by Supabase/cloudSync. Users re-paste on each new browser. Deliberate trade-off: nothing in the DB ever holds the key. The optional **ScrapeCreators** key (Outliers) sits in the same blob under the same rule. Both are written through `snapshot(state)` rather than a hand-built literal — an earlier setter rebuilt an object naming only the fields it knew about, which silently dropped any key added to the shape later. **Both also survive sign-out, via the per-user vault** `ai-ugc-lab-keys` (`adoptUserKeys` / `rememberKeys` in `settingsStore.ts`): `wipeLocalUserData` clears the settings blob so the next person on a shared browser can't inherit a key, which used to mean re-pasting both on every sign-in — since they're the one thing in the app that isn't cloud-recoverable, the wipe was the whole cost. The vault is keyed by user id and adopted **only after** any wipe, so a member restores their own keys and never another's; a member with no entry yet has theirs seeded from the live settings (the upgrade path), and clearing both fields in Settings deletes the entry outright. Cost of the trade: a signed-out member's keys stay on that browser's disk until they clear the fields.

## Announcements and admin

- **Announcements** (migration 0020, Admin → Announcements). The operator's broadcast channel, and the one synced table that is **not a bank**: one global list written by admins and read by everyone, so it skips `bankStore`/`cloudSync` entirely and lives in `stores/announcementStore.ts`, loaded once per sign-in by `components/announcements/AnnouncementsHost.tsx`. Two levels, and the split is the whole design: **`update`** dots the Dashboard tile, **`alert`** *also* opens once as a modal on the member's next load (oldest unread first, one per load) and never again — so an outage can interrupt without training members to dismiss every feature note on sight. Read state is per ACCOUNT (`announcement_reads`, marked after a card holds the viewport ~0.9s, not on panel open), which is also what makes the "seen by 38 / 62" receipts in Admin real; the admin policy on that table stays SELECT-only. `published_at` in the future IS the scheduler — the member-side RLS policy only returns rows whose time has passed and whose `expires_at` hasn't — so nothing polls and drafts are invisible to members by construction. The image is a downscaled JPEG **inline in the row** (`components/announcements/media.ts` caps it), because every R2 key is signed under `auth/<userId>/` and a shared object would need a new public prefix in the presign route; the list query excludes it via the generated `has_image` column and each card fetches its own. A YouTube link needs no image at all — the card derives the thumbnail from the video id. The **preview in the admin editor renders the real `AnnouncementCard`** off the real draft (that's what the card's `preview` flag is for), with a light/dark switch that works because the `light:` variant matches any `[data-theme="light"]` ancestor. Publishing arms first, same two-click contract as delete.
- **Admin panel data.** Every tab stays mounted after first visit, and Members + Insights genuinely share one fetch — a 60s-fresh zustand store in `apps/admin/useMembers.ts` (it claimed to share one before and didn't). Remounting per tab click refired three queries and threw away sort, filters and scroll, which is what made every tab click drop the panel to a spinner. Every admin query goes through `apps/admin/adminQuery.ts`: `readyAdminSession()` first — Admin was the last cloud path not awaiting `ensureFreshSession()`, so its queries queued behind supabase-js's auth lock and only unblocked on a full page reload — then `withTimeout`, which really aborts the request so a late response can't land over fresher state. A failed refresh over loaded rows banners; it never blanks the table. It fetches four things: `profiles`, the `member_storage` and `member_activity` views, and **`member_app_usage`** (migration 0022) — the last one **paged** through `selectAllRows`, unlike the other three, because it returns a row per member PER APP and so crosses PostgREST's 1000-row cap at ~90 members; a silently truncated read there would report an active member as having opened nothing. Insights renders **every** tracked app including the ones at zero (an app merely missing from the chart doesn't answer "is anyone using Outliers", a row reading `Outliers · 0m` does), and Members carries the per-member `Top app / 30d` column and the same figures in the CSV as raw minutes.
- **Deleting a member** (`apps/admin/deleteMember.ts`, driven by the Members table's row checkboxes). Disabling locks an account and keeps everything; deleting removes it — for spam signups, not for members who left. Two steps, in this order: `/api/r2-delete-user` purges every object under `auth/<userId>/` (admin-verified, fails closed; best-effort, so a storage failure warns instead of blocking), then the `admin_delete_member(target_id, remove_from_allowlist)` RPC (migration 0018) deletes the `auth.users` row and every bank/asset/usage row cascades off it. R2 first, because nothing points at those objects once the rows are gone. The RPC refuses to delete an admin or the caller, and removing the allowlist row (default ON) is what stops the person signing straight back up.
