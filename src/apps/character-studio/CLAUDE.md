# Influencers — `character-studio/`

Create section of UGC OS. This file loads when Claude works with files under `src/apps/character-studio/`; the app-wide rules stay in the root [CLAUDE.md](../../../CLAUDE.md).

## Job

**One press can fire up to four characters** (`BatchCountStepper` in the generate bar, capped at 4, default 1) — a portrait is a casting call and the first face is almost never the one you keep, which until now meant pressing Generate four times and watching four separate charges tick past. The run fans out as N parallel `launchGen` calls sharing a `batchId` (with each member's `batchIndex`), stamped onto the in-flight entry AND carried onto the finished `characterHistory` row, because a batch's members land one at a time and the stage has to hold the group across that transition. Generate then **follows the run to the view that can show it, but only ever TOWARDS the grid**: a batch fired from the list goes to Grid, and everything else stays where the member already was — including the Single stage, which is the view people record on, so being thrown out of it on every press would undo a deliberate choice. It used to pull a run of ONE onto that stage, which meant Single was the view members actually sat in whatever the toggle's default said; **the grid is the view** (Massimo's call, August 2026) and only the `Frame` button and the toggle put anyone on the single stage now. **The Single stage takes a LIST of slots, not one item**: 2 side by side, 3 side by side, 4 as a 2×2 (`stageGridClass`), each cell its own `FittedFrame` so a 16:9 sheet and a 9:16 portrait can share a row without either being letterboxed, and each cell swapping from `GeneratingTile` to the grid view's own `HistoryTile` (given a `frameStyle`, which switches its image to `object-contain` in a measured cell) as its member finishes. Slots are resolved by `batchKeyOf` — an unstamped gen is a group of one keyed by its own id, so nothing needs a "batch of 1" branch — and a **pinned** character is deliberately a single cell, because a pin is one face someone chose to have on camera rather than a run. Gens belonging to some other run are counted in the caption (`StageCaption`), never crowded onto the stage. `viewMode` lives in `CharacterStudio` (same localStorage key it always had) so Generate can move it; `GalleryPanel` is still memoized and both new props are stable.

The Physical tab reads **Identity → Face & Skin → Eyes → Hair → Wardrobe**: skin and realism is what decides whether a render reads as a photograph at all, so it's the group a member fills first rather than the one they reach past eye shape and hair texture (August 2026). Form → portrait image, or (Portrait / Influencer Sheet toggle) a multi-panel reference sheet (turnaround + expressions + full body; scene/pose/camera fields ignored; prompt layout swaps with orientation). **The Portrait / Sheet toggle picks the output kind ONLY** — resolution and aspect are shared across both modes and never reset by a flip (both used to, silently undoing a deliberate 4K or 9:16 pick and multiplying the credit cost); a sheet's grid needs a long axis, so 1:1 renders it vertically without touching the stored portrait aspect. Same rule in `InfluencerEditModal`'s Edit Character / Character Sheet toggle, which seeds both settings from the image being edited. Resolution defaults to 1K (key `:resolution:v3`). Sheets save as their own bank Model entry (named like a portrait; stamped as both `characterImage` and `sheetImage`). **Everything in a lineage saves under the source character's name** (`nameGenerator.ts`): the source portrait keeps the bare name, a sheet takes " - Character Sheet", an edit takes the visual style it was rendered in ("Mia - Claymation", off the row's `styleName` stamp) or the next free number ("Mia 2") — `uniqueBankName` dedupes against the bank so two variants can't be offered one name. An unsaved lineage's fallback name is **seeded on the lineage id**, so the modal and the gallery suggest the same person. Horizontal (16:9) outputs span a full row in the gallery, and in `BankPicker` a sheet spans both columns only when its image measures landscape (`onLandscape`) — a 9:16 sheet is a normal one-column tile. The gallery header's view toggle is **Single / List / Grid** (persisted, default Grid): **Single** shows only what's happening now — the running gen, else the newest character — floating on a graph-paper `Stage` (`.stage-grid`, edge-masked), over a row of named action pills and then a collapsed **Prompt data** JSON dropdown (Copy JSON), with a **+** in the header that empties the frame to "Awaiting generation" until a newer generation arrives (`clearedId`, keyed to the newest row's id, so it resets itself). It exists for screen recording, where a reel of past characters is on camera; nothing is deleted and the history is one toggle away. **Single shows the newest character by default, or a pinned one.** The `Frame` button in every grid tile / list row's action stack puts that character on the stage and switches the view there, so the click has a visible result; a `Newest` pill appears in the header to undo it. The pin (`ai-ugc-lab:influencers:single-pin`) stores the id it picked AND which row was newest at the time, so it **retires itself the moment a newer generation lands** — the same self-resetting trick as `clearedId`, and without it finishing a character and finding the stage still holding an older one reads as a failed generation. A pin whose row was since deleted falls through to the newest too. Every `SingleView` callback targets the item actually on the stage; they used to read `characterHistory[0]` directly, which was only ever the same row because the stage was always the newest one. **`InfluencerEditModal` wears the **`SectionCard`** its own controls column has worn since #437 (August 2026) — it was the one surface in this app that never got the shape lifted out of it. Its reference thumbnails and its visual style were two unlabelled affordances stacked on each other, which is why the add card had to pin `Optional` and its count into its own corners; now a **References** card carries both, with the add tile joined into the thumbnail grid (Playground's `RefTiles` shape) and the count on a `SectionLabel`. **Visual Style moved OUT of the prompt box**, where it had ridden as a header row "on top of whatever is typed below": B-Roll made the opposite call for its own style row a week later — the look is something the render is built FROM, like the reference photos — so the app was holding one of each, and the two now agree. No dots in that card: nothing in it gates Generate (the base image does, and it's on the right), so every dot there could only ever be green or neutral. **An in-flight tile is clickable everywhere**** (Single, grid, list) and opens the editor on the generation that is still running — waiting on a render just to reach the controls you were going to use on it was the whole friction. That works because `finishGen` writes the history row under **the generation's own id**, so `GalleryPanel` can anchor the editor by id (`previewId`, not a row snapshot) and the same anchor resolves to the pending gen first and the finished row on arrival, with no remount. `pendingItemFromGen` shapes the gen as the row it's about to become with an **empty `imageRef`**, which is the flag `InfluencerEditModal` reads to return NO outputs rather than a synthetic dead tile — that keeps Generate disabled until there's a base image, and the modal's own in-flight tiles are what's on screen meanwhile (its `lineageInFlight` matches `(g.lineageId ?? g.id)`, since a form gen carries no lineageId). A running gen renders at the shape it will land in — the same `GeneratingTile` as everywhere else, wrapped in an accent glow (a scanning sweep over it was tried and cut: the drifting blobs already read as alive, and the sweep made a calm frame busy). `useFitFrame` sizes the frame to hug the image (aspect ratio + whichever axis runs out first), so the badge and the glow sit on the picture's own edges. **It follows the DECODED file, not the requested ratio** (`useNaturalRatio`, read off the `<img>`'s `naturalWidth/Height` on load; the requested string is only the shape held before a picture exists). The two are routinely different — the picker offers 9:16 / 16:9 / 1:1 and GPT Image 2 answers a 9:16 request with a 1024×1536 file — and `ratioOf` maps every non-16:9, non-1:1 string to 9:16, so a portrait sat `object-contain` in a frame 18% too tall and `bg-black light:bg-zinc-200` painted the letterbox as a pale bar above and below the character. Both fitted surfaces do it: `SingleCard` inline, and the multi-slot stage through `StageCell`, which owns the state its `HistoryTile` reports into (`onNaturalRatio`). The unfitted grid tile never had the bug — it's `block h-auto w-full` and hugs its own image. **Every finished row names the model that drew it** (`item.modelId` was always stored, and the in-flight tile already showed it — only the finished ones didn't): a hover-only label on the grid tile's bottom-left, clear of the action stack and stepping aside for the inline name input like the stack does; a line above the meta pills on the list row, the same shape `InFlightRow` uses so a row reads identically rendering or finished; and `Model · when` on the Single view's caption, the one place a stage holding a single character can state it outright — sitting **directly under the picture** in dim `ink-600`, not at the foot of the card under Prompt data, where it was a lone line of chrome holding the panel's bottom gap open and a caption three controls away from its subject. **`SingleCard` is keyed on its item**, like the multi-slot branch beside it: the stage swaps the character rather than unmounting the card, so without it `TileDeleteButton`'s internal two-click ARMED state carried over and the next character opened already showing "Confirm". Its `useHistoryTileActions` `deleting` flag is scoped to the item id for the same reason and is the bug that made this visible — `confirmDelete` deliberately leaves it SET on success (the tile is about to disappear with its row, and clearing it would flash the button back to life on the way out), which is only safe while the tile actually unmounts; as a bare boolean on the Single stage it stayed true against the row that replaced it, and the `if (deleting) return` guard then refused every further delete behind a spinner that never stopped. **The Load Character Preset / Extract Character DNA pair is a FIXED band** under the tab toggle, outside the scroll container entirely (August 2026). It was a `sticky top-0` child of the scroller, and sticky only pins once the scroll has started: at scroll-top the row sat in normal flow and every overscroll bounce floated it, so two rows that are panel chrome read as loose. A row that must never move doesn't belong inside the thing that moves — the scroller's mask now feathers both its edges instead of the row carrying its own gradient. **That row opens `PresetPickerModal` — a CENTRED modal over one scrolling grid, not the 380px right slide-over it was** (August 2026), and the two scoped pills further down the column (`Physical Presets` / `Scene & Pose Presets`) open the same component with their own title, merging only their tab's keys. **Every SECTION TITLE is the same button one level finer** (August 2026): Identity, Face & Skin, Eyes, Hair, Wardrobe, Pose & Action, Camera and Setting each open the picker scoped to that group's own keys, so a member who likes one template's hair and another's wardrobe can take exactly that rather than the whole recipe or the whole tab. One `PresetPillButton` serves both altitudes through a `tone`: the tab divider keeps the glassy **influencers** tint (it's the line that separates two tabs and has to stay louder than the eight headings under it), and a section title is **neutral ink** — Massimo's call — keeping the heading's own `text-sm font-semibold` and borrowing only the chrome that says *button*, the dashed ring and the chevron. State is the `FieldGroup` being picked for, not a flag per group, and the modal is mounted only while one is open, so a group added to `TABS` gets its own picker with no wiring; `applyScopedPreset`'s `cameraDevice` guard is what keeps the Camera group's pick from blanking the always-on photorealism string. A slide-over is the wrong shape for a picture library: three faces across meant the starters alone ran past a screen, and a member's own characters were only reachable by scrolling past every built-in. The modal gets **six across** at a size a face is still judgeable at and pages the grid in on scroll (`PAGE = 30`, grown from the scroller's own `onScroll` rather than an IntersectionObserver sentinel — the arithmetic is two subtractions and can be watched without a second async system in the middle) so a few hundred image decodes don't mount on open. Card names are **centred**, like every other bank card in the app (`ImageCard`'s own `centerName`) — they were the one left-aligned label. **A card is named `<Scene> <Gender> <n>`** — "Kitchen Female 2" — built by the build script and numbered within its scene + gender group. The export's own descriptive name ("Braided Blonde on the Sofa") describes the picture you can already see; what the label has to say is where this one sits in a library you scan by scene, which is also what the two facets filter by. That name survives as `title`: it's the card's tooltip (with the shot note after it) and it's in the search haystack, so "braided blonde" still finds her. Search covers the whole DNA besides, so "freckles" and "wood slat wall" find the character they describe. **The two libraries are ONE scroll, in labelled sections** (Massimo's call, August 2026): your own characters, then the template library **grouped by style** — "Handheld Mic", "Car", "Kitchen" — one `DayPill` per group, in the library's own order. Splitting on a change of key rather than bucketing is what lets a group page in behind the rows above it. Your own characters stay a SINGLE group: their style is keyword-guessed off free text and plenty of rows have none, so grouping those would file the same face under a different heading each time it was extracted. They were a toggle that swapped the grid for a week, on the theory that a member with 35 characters shouldn't scroll past all of them to reach a template — the jump below is the cheaper answer to that, and it keeps everything the picker holds in one list you can simply keep scrolling. The **`SegmentedToggle` above the filter row survives as that jump**, with a count on each side (Your Characters — "Yours" below `sm`, where the full wording truncated — / Templates): clicking scrolls to that section, raising the page count first so the rows above it exist to be scrolled past, and the highlight FOLLOWS the scroll rather than the other way round. Both are measured with `getBoundingClientRect`, never `offsetTop` (`sectionTopWithin`): the scroller isn't a positioned element, so a section's `offsetTop` is counted from the modal panel and carries the header + filter bar with it — about a row of cards' worth of error, which is exactly how far the jump used to overshoot. An empty bank renders no section of its own, so the highlight is DERIVED past the tracker there (`bankCount === 0 ? 'starter'`) rather than seeded by an effect, or a new member opens on a grid of templates with "Your Characters" lit. Stacked as two sections, a member's own characters were a band at the top that anyone with 35 of them scrolled past to reach a template. Which side opens is **derived, not stored** (`sourcePick` is `null` until a click, and falls back to the bank when it has rows): an effect correcting it after the first render is both a cascading-render lint error and a frame of the wrong tab. Clicking onto an empty bank is allowed — the badge reads 0 and the grid says "No saved characters yet.", which beats a segment that ignores you. Narrowing the list resets the page count AND the scroll, or a filter applied after scrolling to card 200 renders 200 cards of a 12-card result. The two library counts are tallied against search and gender but **not** against the scene, so a scene picked on one side can't make the other side's badge promise a number the grid won't deliver. **Two facets on one bar with the search box: Gender as a `SegmentedToggle`, Style as a `Dropdown`** (both facets serve BOTH libraries — the style menu was hidden on the bank side for an afternoon and came back on Massimo's call). The rows call that field `setting` and always will — it's the build script's own word for the shot category — but the member's word for it is **Style** (Massimo's call, August 2026): "Handheld Mic" and "Talking Head" are how a shot is shot, not where it is, and the two the library really does name by place (Kitchen, Car) are still styles of UGC ad, both in the influencers accent — as faint neutral triggers on this panel's surface they were reported as invisible. Three options are worth seeing without a click; eleven are not, and as a toggle the scenes made a strip no window fits that pushed the grid down a row. Counts are derived from the rows and tallied against the OTHER active filter, so a library that grows a new scene grows both controls on its own and a count can never promise more than the grid delivers. **Shot type (Close-up / Medium / Full body) was a third facet and was cut**: a starter is picked by who and where, and three framings across the library mostly shrank the grid without answering anything. **Nothing in the bar may move when you use it**, which takes three rules, all of them reported before they were found. Every count renders in a fixed-width `CountSlot` (`min-w-[2ch]` + `tabular-nums`), because a live count going from "All 76" to "All 9" takes ~5px with it and slides every segment to its right. The style trigger takes a **fixed 190px** rather than fitting its content, because its label swings from "All Styles" to "Holding Product" and a self-resizing trigger shoves the gender toggle along the row on every pick. And the style options keep the **library's own order** (the source folder's shot numbering, baked into the row order by the build script) rather than sorting by count, which would reshuffle the list between two openings. Every option always renders, including at zero — a vanishing one moves the control too, and a badge reading 0 answers "why is there nothing here" outright (a style with nothing under the picked gender reads 0 rather than vanishing). Measured at 0px drift on both controls, in both directions. **The panel is `z-[60]`, not the `z-[70]` a picker would normally take.** `AnchoredPopover` portals every menu in the app at `z-[60]` over a `z-[55]` catcher — the lowest overlay tier, since its job is escaping a scrolling panel's clip, not covering a modal — so at `z-[70]` this panel painted over its own style menu, which is what "the dropdown opens behind the modal" was. Sharing the tier lets DOM order decide and the menu, appended to the body later, wins: the same arrangement `InfluencerEditModal` and its chips rely on. The style menu is exactly such a menu, so the tier is load-bearing — don't raise it. Gender is **bucketed** rather than matched (`genderBucket`), because a bank row's profile is free text and a facet built from raw values lists two spellings of one thing; a bank row's style is keyword-matched off its `location` + `background`, which is a guess, but a guess that files it under the right style more often than not filing it at all. The **starters are static files** — `public/presets/library.json` built by `scripts/build-character-presets.py`, fetched on first open and never before (nothing pays 252KB for a picker that isn't used) — and the nine `PRESET_*` consts they replaced are gone from `types.ts` along with their bundled JPEGs. Their pictures ship in **two tiers**, and the split is load-bearing. The cover was 400px on its long edge and came out **223x400**, against a card that is ~155 CSS px wide — 310 device px on the 2x screens these are looked at on — so every face in the library was upscaled from a picture smaller than the hole it sat in; it was reported as simply looking low quality, and `thumbs/` is 502x900 at q80 (~37KB) now. `full/` is the source's own 768x1376 at q85, and it is fetched **only when a member saves that template**, which is why the grid doesn't pay its ~105KB a card. **Templates become bank rows, and that is how they reach every other app** (`saveStarterToBank`, August 2026): until then a member could load a face into the form and still not attach that face anywhere — the DNA travelled and the picture didn't. A bank row is the app's own answer to "use this character elsewhere", so saving puts the full portrait in IndexedDB (mirrored to R2) under a real `Model`, pickable in Playground, B-Roll and Scripts by the route a generated character already takes. **Two ways in.** Here, a `TileActionStack` on the card saves it outright. Everywhere else, **`BankPicker` offers the whole library inside its characters bank** (Massimo's call, August 2026 — "use the templates just as I would my own characters"): the unsaved ones render as stand-in `Model`s under the same style headings, and PICKING one writes it in and hands the caller the row it just became, so nothing downstream ever receives a `Model` whose `characterImage` is a static URL it can't keep. That picker carries **the same two facets** as this one — a bucketed Gender toggle and the Style menu, both counted against the other and both filtering the member's own rows as well as the templates — and its style menu is the one caller of `Dropdown`'s `tier="panel"`, because `AnchoredPopover` defaults to the app's LOWEST overlay tier and the picker's slide-over is `z-[80]`: at the default tier the trigger visibly opened onto nothing. `flattenJsonProfile`, `genderBucket`, `settingFromProfile` and `buildSearch` all live in `presets/service.ts` so the two pickers facet and search by one copy. The row stamps **`Model.presetId`**, which is what draws the green tick on a template already saved — matching on the name can't, since the member is free to rename it afterwards — and the bank name is the export's descriptive `title` ("Braided Blonde on the Sofa"), not the card's "Handheld Mic Female 1": in a bank of characters a scene-and-index label says nothing about which face it is. The rule those nine were written to demonstrate still governs anything added to that folder: every field filled, and the DETAILED option wherever the field offers one. `InfluencerEditModal`'s reference thumbnails are the shared 64px `ImageTile` / `AddTile` (`components/video/refInputParts`), not a four-up `grid` of `aspect-square` cells, which drew each one ~110px in that half-modal column. **The editor's outputs gallery is TWO across and day-grouped** (August 2026): it packed three to a row, but that column is half a modal, so the third tile cost every face the size it needed to be judged at — which is the only thing that gallery is for. It matches the main gallery's base grid now (`grid-cols-2`, landscapes spanning the row) and carries that gallery's `DayPill`s, so a lineage edited across several days reads in here the way it reads out there; `SessionOutput` gained the `createdAt` it needed to group by. Drop a reference photo anywhere to auto-fill every field via vision-based DNA extraction. **Every analysed photo lands in the reference library** (`useReferenceLibrary` + `ReferenceLibrarySlideOver`): the **Extract Character DNA** row opens it — the whole row, plus a chevron, exactly like the Load Character Preset row it sits beside — rather than a bare file dialog, since browsing, bulk-adding and reusing an old analysis all live in the panel (which has its own drop zone); dropping straight on the row still works. It's a right-edge slide-over that takes a **bulk** drop (3 at a time, `runPool`), lists each analysis day-grouped under a `DayPill` with its own DNA one-liner (`describeRefProfile`), and refills the form from any row on a click — so a face is analysed once, not once per session. A lone dropped photo still fills the form the moment it lands; a bulk drop never does — the member picks. **Every nested drop zone MUST `stopPropagation()`.** `CharacterStudio`'s root div carries a full-area drop handler that also calls `addFiles`, and React synthetic events travel the REACT tree (so a body-portaled `SlideOver` is still a child of it) — without the stop, one drop on the DNA pill or in the library ran `addFiles` twice: two rows, two vision calls, two charges on the member's key, and the form auto-filled twice. `addFiles` also keeps a short signature-keyed dedup window (`DOUBLE_FIRE_WINDOW_MS`) as belt-and-braces, since it is the entry every path shares and a vision call costs real credits. The library is deliberately **local-only and thumbnail-only**: rows persist to localStorage (capped at 60, newest-first) carrying the extracted `profile` plus a ~224px JPEG data URI (`utils/thumbnail.ts`), because nothing re-sends a reference photo after its one vision call, and keeping the full-size original would mean an IndexedDB asset no bank row points at — which the orphan sweep deletes on the next sign-in. State lives in `CharacterStudio`, not the panel, so a batch keeps running with it closed; `activeRefId` (persisted) is the pointer the autofill pill and the library share, and clearing it detaches the reference without deleting the row (the library is history, so "New" leaves it alone). A row with neither a profile nor a live analysis failed — its Retry is offered only while the source file is still in session memory, since only the thumbnail survives a refresh. Display name rebranded from "Characters" — folder, ids, types, and LLM prompts keep the character naming.
