# Compositing and render cost

The rules behind a whole class of "the app feels laggy" reports. The root
`CLAUDE.md` states each in one line and sends you here. **Read it before
adding a `backdrop-filter`, making a bar `sticky`, animating opacity over
generated media, or putting a list beside an input.**

The through-line: this app puts dozens of animating, blurred, generating media
tiles on one screen. A cost that is invisible on one card is the frame budget
on twelve.

- **A history panel next to an input panel is `memo`'d, and its props are stable.** The history banks are uncapped (only `brollHistory` has a cap), so a working member's gallery is hundreds of rows, each with its own asset lookup — and it sits in the same component as the box they're typing into. One fresh callback identity per render means every character typed re-renders the whole list: measured at ~70 ms (Playground) and ~85 ms (Characters) per keystroke at 300 items, versus ~4–10 ms once the subtree is skipped. `PlaygroundHistoryGrid` and Characters' `GalleryPanel` are the two wired this way — `memo` on the panel, `useCallback` with only stable deps on every handler it takes, and the live draft read through a ref rather than closed over. The React Compiler does this on its own for components it can compile, so the explicit `memo` is a belt-and-braces for the app roots that still bail (see Tech Stack).

- **A list of media resolves its pictures near the window, not on mount.** The history banks are uncapped, so a working member's gallery is hundreds of rows — and each row used to hand the browser a full-size picture to decode the moment the panel mounted. Measured on Characters with 250 rows (462 KB JPEGs, 1024²): **every one of the 250 resolved a blob URL and decoded, with nine on screen.** The JS heap reads a reassuring ~58 MB throughout, which is the trap — a decoded bitmap and the Blob behind its object URL both live OUTSIDE the JS heap, so the number that looks fine is measuring the one thing that is. At 1024² the real figure is up to a gigabyte of bitmap.

  `loading="lazy"` does **not** fix this and its presence is what makes the bug hard to see: it defers a *fetch*, and by the time the `<img>` exists the blob URL has already been made — the read, the object URL and the decode have all happened. What actually works is gating the resolution itself: `useNearViewport` (`hooks/useNearViewport.ts`) claims media as a tile scrolls in and releases it once it's well clear, so the live count tracks the window rather than the history. Same measurement after: **250 → 15**, exactly five full rows for a 709px port plus the 400px margin.

  Two things make it safe, and both are worth checking before wiring it into a new surface. The placeholder branch must already be **sized by its own geometry** (Characters' tiles carry `aspectStyle`, its list rows an explicit `aspectRatio`), or the scroll height collapses as pictures come and go and every tile ends up "near" anyway — the measured `scrollHeight` is identical before and after, which is the test. And the tile's **actions must not read the gated URL**: Characters' `handleDownload` re-resolves through `getUrl` on its own, so nothing on the tile changes behaviour whether it has painted or not. Pass the SCROLLER as the observer root, never the viewport — ancestor clipping is applied before `rootMargin`, so a viewport-rooted observer only fires once a tile is already on screen and the picture pops in under the pointer.

  Wired in Playground's history grid and (September 2026) Characters' gallery, in both its Grid and List views. **The same eager-resolve is still live in B-Roll's history, the Bank's B-Rolls tab and Outliers' result cards** — same fix, not yet applied. Note when testing: a hidden browser tab suspends IntersectionObserver delivery entirely (a freshly-created observer on an on-screen element does not fire at all), so a gated grid looks permanently blank in a backgrounded pane and proves nothing either way.

- **`backdrop-filter` is for small chrome, and `filter: blur()` never animates.** The one rule behind a whole class of "the app feels laggy" reports, fixed in August 2026. A `backdrop-filter` element is a **backdrop root**: a repaint anywhere inside it invalidates its entire backdrop. `App.tsx`'s workspace pane — which contains the whole workspace — carried `backdrop-blur-xl`, so every animating pixel in every app dragged a full-viewport filter recompute behind it. What it bought was nothing: behind it is `AppBackground`, a smooth dithered gradient, and a blurred smooth gradient is the same gradient. It's a plain unpainted pane now (the rounded, bordered floating "window" frame around it came off in August 2026 too — the pane fills the space between the menu bar and the dock flush, so nothing draws a box around the apps), and removing it is why generation animations stopped stuttering, why zoom stopped lagging (a zoom re-rasters everything, backdrops included), and why images stopped looking blocky — a browser under that much compositing pressure drops its raster scale. Keep `backdrop-filter` on small static chrome over real content, and never put one on a full-window container. **`GeneratingBackdrop` is where this rule was finally paid off in full, and how it was done is the point.** Its three drifting blobs each carried a live `blur-2xl`, on a surface whose whole job is to appear a dozen at a time — so a storyboard batch meant three dozen full-size Gaussians per frame. Two earlier goes only bent the curve: rewriting the blobs as radial gradients was reverted within the hour (a gradient's falloff is a linear ramp where a Gaussian's is a smooth curve, so the plateau edge reads as banded lobes instead of one soft wash, and this is a glow whose entire job is to look good while someone waits), and taking the `scale()` out of the `blob-drift-*` keyframes helped without fixing it — the translate alone was still enough to keep every filtered layer dirty. Measured on a grid of backdrops and nothing else, 12 tiles / 24 tiles: **live blur 63 / 36 fps** (worst frame 18ms / 34ms), **one shared filter over all three blobs 114 / 64 fps**, **the Gaussian baked into a mask 120 / 120 fps** — flat, because no filter runs per frame at all. That third one shipped. `.gen-blob` masks a flat accent fill with an SVG whose white circle is blurred by a real `feGaussianBlur`: the browser rasterises the mask once and the blob is a picture being moved from then on. It is the same Gaussian curve as before, drawn ahead of time — **not** the gradient that was reverted, so don't "simplify" it into one. Two things it costs: a mask cannot paint outside its element the way a filter can, so the blob boxes are ~2.1× the old ones around the same centres and the mask's circle and those boxes have to be resized together; and if the blur ever needs to change, change the mask's `stdDeviation`, never put `filter` back on something that moves.

  **And it still wasn't enough — so the drift is gone too (August 2026).** The 120/120 row above is a grid of backdrops and *nothing else*, which is exactly why it read as fixed and wasn't: baking the blur removed the per-frame Gaussian, but a moving element is still a composited layer of its own, and these are ~2× the tile, three per tile, on every card of a storyboard batch. At 24 tiles that is ~70 large GPU textures being held and blended behind a real app that also has to draw storyboard cards, `<video>` elements and panel chrome — and a browser under that much compositing pressure drops its raster scale and starts landing frames late again, which is what was still being reported. A **static** masked lobe promotes nothing: it is painted straight into the tile and costs nothing per frame. The look is unchanged — same three lobes, same Gaussian, same tinted base — and what carries "something is happening" is what always actually carried it: the indeterminate bar sweeping under the status line, the status line rotating every 4s, and one slow alpha breathe (`.gen-lobes`, 6s) over the three lobes as a group. That breathe is deliberately on the **wrapper**, not on each lobe: opacity is the cheapest property there is to animate (the layer rasterises once and only its alpha varies), and one wrapper means one composited layer per tile instead of three. The wrapper is `overflow-hidden` so that layer is exactly tile-sized — without the clip its bounds would be the union of three 2× boxes, which is the texture footprint the change exists to remove. `still` on `GeneratingBackdrop` drops the breathe as well, for the decorative (non-generating) use on the Bank's preset covers. `offscreen-idle` (`content-visibility: auto`, #459) still skips tiles that are off screen, which now also defers the mask raster until one scrolls in. Its base gradient carries a **faint** accent tint over the ink ramp rather than neutral grey (Massimo's call) — a full accent wash was tried and was too much; the grey is what makes the tile read as frosted glass rather than as a coloured card.

  The other half landed with it: **no `backdrop-filter` may sit on top of this backdrop.** The mode glyph and the cancel/dismiss buttons on every generating tile wore `backdrop-blur-sm`, and a backdrop-filter re-samples and re-blurs its patch on every frame the thing behind it changes — one per generating tile, all of them over an animating surface. They take a slightly heavier flat scrim instead, which reads the same over a soft wash. This applies to chrome that merely *happens* to be on screen while the tile generates, not only to chrome the generating tile renders itself: Continuous' "Option N" pill is rendered outside the in-flight branch, so it sat blurred over the backdrop on all three option cards of every frame and was missed twice. When adding a pill to a media card, check what the card looks like mid-generation.

- **A loading pane breathes as a GROUP; individual skeletons don't shimmer.** Same rule as the generating backdrop above, found the same way — one screen at a time. Each `.skeleton` carried an `::after` sweeping across it under a transform, which was already the cheap version (an animated `background-position` repaints the element every frame and stuttered visibly). But a transform still promotes that pseudo-element to a composited layer, and every one of them sits inside a `border-radius` + `overflow: hidden` parent — the case WebKit is worst at, where a rounded clip over a moving layer either costs a clip/mask layer per skeleton or drops the child off the fast path and repaints the parent every frame. B-Roll's Line-by-Line loading pane renders 3 scenes × 6 skeletons = **eighteen** of them, nine at full 9:16 card size, and that is what was reported as lag while the storyboard was being written (Safari, August 2026) — a separate report from the generating-tile one, on a screen that never shows a generating tile. So the sweep is gone and `.skeleton` is a flat block; `.skeleton-group` puts one slow alpha breathe on the **wrapper**, which is one composited layer for the whole pane instead of one per skeleton. Every pane that uses these already has a `GenerationProgress` bar and a rotating status line above it — that is what actually says the work is running, and eighteen shimmer bars underneath were decoration on top of a signal already there. Wired in B-Roll's two loading panes and Scripts' output panel. Don't put an animation back on `.skeleton` itself; wrap the block.

- **Chrome that must not move lives OUTSIDE the scroller, not `sticky` inside it.** B-Roll's two storyboard strips were `sticky top-0` glass bars inside the scroll port, and they visibly came loose from the top edge on the way back up a long storyboard: a backdrop-filter element re-samples its backdrop on the main thread while the scroller is scrolled by the compositor, so the bar lagged its own container by a frame or two and snapped back. Both are static `shrink-0` rows above the scroll port now — a sibling of the scrolling box, exactly like the panel header above them — which makes the pinning structural rather than something the compositor has to keep agreeing to. Ask first whether the bar ever actually scrolls away: neither of these did (both were pinned at `top-0` from the first pixel), so `sticky` was buying nothing but the artifact. The cost is that content no longer passes under them blurred, so they take the **opaque** fill (glass over a panel background that never moves is a backdrop root's cost for no picture) and keep `relative z-20` so a card's own positioned hover chrome can't paint over them. When a bar genuinely does have to scroll away and come back, `sticky` is still the tool — just don't also make it glass.

- **Pinned panel chrome is glass, and anything that FADES on hover is not.** Two halves of one backdrop-filter rule. A bar that stays put over content it doesn't scroll with (B-Roll's panel header) takes `supports-[backdrop-filter]:bg-surface-0/80 + backdrop-blur-xl + backdrop-saturate-150` over an opaque `bg-surface-0` fallback: content passing under it blurred is what makes it read as a fixed pane of the panel rather than a card-shaped hole, and a nested backdrop-filter DOES blur inside a parent `backdrop-blur-xl` (the earlier "it can't re-blur" note was wrong — what made a translucent strip read as scrolling was too little blur and no saturation). The opposite holds for anything animating its own opacity: a backdrop-filter re-samples its backdrop every frame, so a hover-faded overlay over a real generated still stutters — which is why `TileActionStack` has never had one, and why B-Roll's variation-card shortcut row, tag chip and status badges dropped theirs (an empty card never showed it; a flat face is nothing to blur).

- **A page that is idle must produce no frames — so nothing on it may animate forever.** The Dashboard is the app's DEFAULT landing page and it had permanent motion in two layers: a nine-planet orrery on eighteen rotating arms, and a wallpaper whose two full-viewport starfields drifted and breathed while a meteor crossed every 22 seconds. Every one of those was the *good* kind of animation — `transform` and `opacity` only, composited, no layout, no repaint, no JS per frame, and the drift had already been moved off `background-position` for exactly that reason. It still cost real CPU, because of what sits on top: **ten `backdrop-filter` widgets**, and a backdrop-filter has to re-run whenever its backdrop changes. Any motion down there, however slow, meant ten Gaussians every frame at the display's refresh rate (120 Hz on a Mac laptop), forever, on a page where nothing was happening. Measured by A/B-ing the orrery against itself in the live page — a toggler flipping it every 10 s while an outside sampler read the renderer's CPU each second, 160 buckets over 3 minutes, which is what it takes to see through the noise: **11.8% of one core with it, 7.9% without, against 0.1% for a blank page.** Both are gone (September 2026): the orrery deleted, then the sky made still and finally deleted too, leaving the widgets on the shared page gradient. Two things to take from it. The first is that "it's only a composited transform" is an argument about the *animation*, not about the *page* — ask what is layered over the thing that moves before you call it free. The second is that a still sky costs literally nothing: the page is painted once and then left alone, which is the only state in which a laptop's fans and battery notice anything at all. What remains on the Dashboard is the menu bar's `animate-ping` alert dot, which is chrome on every page and only exists until a member saves a kie key — if that ever needs to go, it goes for the same reason.
